# API 契约整理

## 要做什么

- 按目录或 tag 分批核对接口。证据优先级依次是真实响应、当前项目调用、旧项目调用和已有 OpenAPI。
- 使用 curl 或 Apifox 请求接口。需要鉴权时向用户获取环境变量、token 或账号；写接口只在用户确认影响范围后调用。
- 补齐 Zod Schema、字段说明、接口说明和响应说明，重新生成 OpenAPI，并检查 Apifox 的导入结果。
- 保留接口的验证状态和来源，运行现有契约测试、生成物检查、类型检查和构建。只有现有测试无法覆盖真实契约变化时才补最小回归用例。

## 你对我的约束

- 后端响应允许字段缺失、为 `null` 或带有额外字段。没有充分证据时，不删除 `optional`、`nullable` 或 `looseObject`，也不根据单个 fixture 收紧契约。
- `description` 只写接口行为和字段含义。验证状态、探测过程和响应是否实测等信息放在 `x-cc98-verification`、执行计划或 PR 中，不写进公开说明。
- 普通说明使用标准 OpenAPI `description`。只有标准规范无法表达且 Apifox 确实需要时，才增加 `x-apifox-*` 扩展。
- 找不到字段含义时写“具体含义尚未确认”；原项目没有使用该字段时，可以明确说明原因。不凭字段名补造定义，也不反复解释调查过程。
- 不单独建立证据表，不预先增加测试文件或新测试体系。调研记录留在执行计划或 PR，测试复用现有入口。
- 无法成功调用的管理接口保留原验证状态，不要求补齐成功响应证据，也不把“未验证”写进接口或响应描述。
